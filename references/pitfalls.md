# 九族反复踩的坑

长期沉淀，按"病灶类型"归成九族。审查任何改动时，逐族扫一遍——**返工第二次的地方，一定是这里某一族**。

---

## A 族：门禁假绿 / 空门（最高频，优先扫）

病根：门写了，但它根本没在拦东西。

- 负控不红的断言＝没有断言，绿门数不等于门数。
- "测试全绿是绿在错误前提上"——错误前提被写进冒烟 fixture，锁死了。
- 写完任何门，先在"已知坏"的状态上跑一次，看它会不会红。（一次门极性写反，五道门全绿，把运行时从 22 降回 20.20.2。）
- 门没配 remote / 没 fetch **不算通过**；静默跳过＝这道门永远绿。
- 门只核单向祖先，一棵落后远端 10 笔的树照样绿。

**扫法**：随便挑一条门，问"它上次变红是什么时候"。答不上来 = 空门。

---

## B 族：负控工具自身的坑

病根：负控做了，但负控本身是坏的。

- 改坏→跑→还原的脚本只在最后统一还原 ⇒ 第二、三发继承第一发的改动，报的"咬点"其实是第一发的，**读数无效**。
- 负控样本本身没验 ⇒ 假负控（拿一个本来就好的提交当"已知坏"样本）。
- 按 `\n` 改文件，在 CRLF 树下静默失配 ⇒ 假绿。改不含换行的子串，或按字节流操作。

**扫法**：看负控脚本有没有"逐发还原 + 同次运行核哈希"。没有就重跑。`tools/negctl.py` 用"一进程一发 + 字节流替换 + 还原后核 sha256"把这三条焊死了。

---

## C 族：静默失败（rc=0 但什么都没做）

病根：命令返回成功，实际什么也没发生。这族最危险，因为**看起来是绿的**。

- `git apply` 在仓库子目录里按仓库根解析路径 ⇒ **rc=0 却静默 no-op**。
- `git grep -- <不存在的路径>` 的 rc=1 会冒充"0 命中"。
- `--since` 传带秒的 `HH:MM:SS` ⇒ NaN ⇒ 恒假 ⇒ 印成 `(none)`，看起来像"没人交件"。
- 管道后的 rc 不是命令的 rc。
- `git log -G` 不吃 PCRE，且把非零码当 0 ⇒ 门禁永久假绿。

**扫法**：任何"0 命中 / 没找到 / 没人提交"的结论，先问"命令本身会不会失败"。

---

## D 族：记账 / 锚点坑（吞历史）

病根：写进台账的动作本身把信息弄丢了。

- **置顶插入会吞标题**——一天犯过三次。落笔后立刻 `grep -c '^## '`，必须恰好 +1。
- 时间列写 `2026-10-23 22:3x` 这种带 `x` 的占位 ⇒ 同步闸判坏行 ⇒ **这一整条从来没出现在台账里**。`x` 占位只许出现在正文，不许出现在日期列。

**扫法**：追加记录后，数一次标题计数；同步闸跑一次 `--dry-run` 看有没有 `SKIP-INVALID`。

---

## E 族：并发写者 / 读数过期

病根：你读的现场，在你读的过程中变了。

- 多会话同写一个分支 ⇒ 你提交前 HEAD 已被别人推进。
- 多会话同写记忆目录 ⇒ 改前没重读，覆盖了别人的。
- **只认 git 内容，不认 mtime**——实测 `find -newermt` 会出假 0。
- 结论级读数**落笔前重取一次**。

**扫法**：报告里的每个 sha，在交付前重跑一次 `git rev-parse`，对不上就全文重取行号。

---

## F 族：度量假信号（尺子量错了对象）

病根：数字是对的，但量的不是你要的东西。

- **CF 邮箱混淆冒充"内容变化"**——逐字符定位差在 `data-cfemail`，实际线上内容没变。
- **体检尺子只看首页** ⇒ 两条假红，是对象集错位。
- **同义反复的负控**——"残留件与钉值件同名，删不删都过"，看起来做了负控，实际什么也没验。

**扫法**：问"这个数字变好/变坏，是因为**我要它变的东西**变了吗"。

---

## G 族：自己造的返工（推翻自己）

病根：上一轮的错误结论被这一轮继承。

- 把"快照提升"当成"只提升写成功的行" ⇒ 结论错了一轮才发现。
- 第一性原理对号，实测否掉自己刚写的方案（例：方案里写的"扫目录 + fontkit 取字体清单"，实测两条来源 1293 vs 1587、只重合 1235 ⇒ 扫目录不能当权威源）。
- 三路回包收齐后，**主假设被自己派的件推翻**。

**规矩**：推翻自己必须**记在报告显眼处**，不许静默改口。已交付的报告要加更正块。

---

## H 族：环境 / 时区 / 权限错配

病根：代码没问题，环境让它表现得有问题。

- `file:` 相对路径经 node_modules 符号链接会**静默读到另一个分支的共享库**——已三次实证。隔离验证一律写**绝对路径**。
- 只认"运行中的进程 + 它实际读的库"，**不认"树里配置应该是什么"**。
- 服务端 nginx 用 CST、子系统日志用 UTC，**差整 8 小时**——对时间线前必须先对齐时区。
- 按镜像名杀进程，连带杀掉同事的浏览器。**进程收尾只按 PID。**

---

## I 族：自己写的并发脚本有竞态

病根：并发代码最容易在你最信任它的时候坏。

- 并发上传脚本竞态，坏在盘上。教训：**不信 `wait` 的返回，逐块轮询到期望字节数 + 逐块 sha256 相同才允许拼接。**

---

## J 族：改了表面，真卡点在别处（特有但极常见）

病根：审的层不对。UI 改了三轮，真卡点是子系统验票超时和回调地址写死。

**扫法**：改完之后现象还在 → **禁止在当前层继续打转**，强制写下"下一层是什么"，至少钻两层。见 `drilling.md` 第一节。

---

## 快速扫描清单

审查任何改动时，花 60 秒过一遍：

- [ ] 这道门上次变红是什么时候？（A）
- [ ] 负控做了吗？逐发还原了吗？（A/B）
- [ ] 有没有"0 命中/没找到"的结论？探针自证了吗？（B/C）
- [ ] 追加记录后，标题计数对吗？日期列有占位符吗？（D）
- [ ] 报告里的 sha 现在还对吗？（E）
- [ ] 这个数字量的是我要的东西吗？（F）
- [ ] 我有没有在继承上一轮的错误结论？（G）
- [ ] 隔离验证用绝对路径了吗？时区对齐了吗？（H）
- [ ] 改完现象还在吗？要不要往下钻一层？（J）
