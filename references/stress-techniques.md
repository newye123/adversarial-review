# 压力测试技巧：钻到最深处的七种刀法

来源：fullo/claude-adversarial-skill、sidtheone/insightsloop、ase-meta-why（均为 GitHub 上的 Claude skill，已抓原文）。思想源头是**混沌工程**（Chaos Engineering）——不问"哪里会坏"，问"什么条件下会坏"。

这是本 skill 里最锋利的一层。前几层（分路取证、负控、IS/IS-NOT）回答的是"审什么"；这一层回答的是**"往哪个方向使劲挖"**。

---

## 核心机制：强制多样性（forced variety）

**每次审查至少用 3 种不同技巧，且不许重复用同一招。**

这条规则不是装饰。没有它，审查者会一直用自己最顺手的那一招（通常是"看有没有明显 bug"），对同一类问题挖一百遍，对别的方向一遍不挖。

```
本轮已用：Existence Question、Time Travel、Cross-Seam Probe
本轮禁止再用：以上三种
必须从剩余四种里再选：Scale Shift / Requirement Inversion / Delete Probe / Replay Probe
```

---

## 七种刀法

### 1. 存在性质疑（Existence Question）

**问**：这东西该存在吗？

**做法**：在脑子里把它删掉——如果什么都不坏，它就不该存在。

**适用对象**：抽象层、包装器、工具函数、"以防万一"加的中间层。

这是**对抗审查最容易漏的一类**，因为审查者天然在审"这段代码写得对不对"，很少审"这段代码该不该有"。对应的真实病：过度工程——Anthropic 官方警告"追着每条 finding 改会导致多余的抽象层、防御性代码"。这把刀反着用，专门砍多余的。

### 2. 规模跳变（Scale Shift）

**问**：10 倍会怎样？0 倍会怎样？负数会怎样？

**适用对象**：数据结构、API、配置、批量操作。

对应的真实病：批量上限没随规模放大、单根目录递归。规模一变，很多"当前正确"的代码立刻不正确。

### 3. 时间旅行（Time Travel）

**问**：6 个月后下一个接手的人读这段，会踩什么坑？哪些假设已经过期？

**适用对象**：聪明代码、隐式依赖、没写下来的决策。

对应的真实病：写死的子系统版本、钉死的 buildId、跨会话并发改同一分支后行号全漂。

### 4. 需求反转（Requirement Inversion）

**问**：如果用户要的是**完全相反**的东西呢？这套推理还剩多少？

**适用对象**：功能开关、配置、业务规则、API 契约。

对应的真实病：**门的极性写反**（实测：五道门全绿，把运行时从 22 降回 20.20.2）。极性反了但测试还绿，说明测试只验了"值对不对"，没验"方向对不对"。

### 5. 跨接缝探针（Cross-Seam Probe）

**问**：两个模块**相接的地方**，两边的假设一致吗？

**适用对象**：任何 A 调 B 的边界。

这是**最容易藏 bug 的地方**——每个模块单独看都对，接缝处两边对"输入长什么样"的假设不同。对应的真实病：安装绑定漂移——两边各自都对，接缝处 installId 不是同一个。

### 6. 删除探针（Delete Probe）

**问**：整个删掉会怎样？

比 Existence Question 更狠——不只问"该不该存在"，是**真删一次**看什么炸。炸的东西就是它的隐式依赖清单。

### 7. 重放探针（Replay Probe）

**问**：拿**完全相同的输入**再跑一次，会怎样？

**适用对象**：任何有副作用的操作、幂等性要求。

对应的真实病：重复激活、重复投影、重复部署。"跑两次结果一样"是很多系统没验过的基本性质。

## 每条结论都要带 Survived 判定

这是本套方法**最反直觉也最有价值的一条**：

```
Survived: yes  ← 这条经过压力测试，站住了
Survived: no   ← 这条在压力下垮了
```

原文立场："resilience confirmed is as valuable as weakness found"——**确认了什么是稳的，和发现了什么是脆的，一样有价值**。

为什么重要：只报"哪里坏了"的审查，会让人对**没被提到的部分**产生虚假安全感。报出"这些经受住了 X 倍规模/时间旅行/需求反转"，等于把审查的覆盖面显式化了——没报 Survived 的地方，就是没审过的地方。

`tools/check_report.py` 的 E011 就是钉这条：有压力测试节却没有任何 `Survived:` 判定，直接判不合格。

## 配套：审查者的怀疑清单（suspicion scaffold）

来自同一套方法的五个模块，直接可抄进审查者 prompt：

| 模块 | 问什么 | 动作 |
|---|---|---|
| **怀疑建模** | 一个普通审查者会漏掉什么？ | 专攻"看起来安全但藏着复杂度"的代码 |
| **攻击选型** | 哪些声明风险最高？ | 按 **爆炸半径 × 概率** 排序，先验最高风险的 |
| **计划合成** | 哪些多步链路会暴露问题？ | 设计链：追 A → 依赖 B → 副作用 C |
| **执行核实** | 我真的逐行看了吗？ | 确认你读了**实际的行**，不要凭记忆推理 |
| **隐蔽检测** | 什么看起来干净实则藏着复杂度？ | 标记：有副作用的一行代码、无害的默认值、"临时"hack |

最后一条尤其对应真实病：`http://localhost:3000` 这个写死的回调地址，就是一个"看起来无害的默认值"藏了几个月。

## 配套：把 finding 抽象成失败类别

不要只报单个 bug。**找到模式，不是只找到一个实例。**

```
❌ "src/auth.ts:42 的 user 可能是 undefined"
✅ "本次改动里有 3 处直接解构服务返回值而没判空（auth.ts:42、folder.ts:18、scan.ts:77）
    ——失败类别：本机服务返回结构未被信任边界拦截"
```

发现一个 bug 时，**同类一起找齐，按类别报一条，不挤牙膏**。这既是效率问题，也是判断力问题——只看到一个实例，说明你没看见类别。

---

## 用法建议

不是每条 finding 都要过七把刀。用法是：

1. 先跑常规审查（分路取证 → 主审证伪 → 负控）
2. 对**活下来的结论**（认为没问题的），抽 3 把刀压力测试
3. 报告里给每条过刀的结论标 `Survived: yes/no`
4. `Survived: no` 的立刻升级为 finding
5. **没过刀的部分，在报告里明说"未做压力测试"**——不许让人误以为全覆盖了
