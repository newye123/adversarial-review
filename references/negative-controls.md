# 负控：证明门真的拦得住

> "负控不红的断言＝没有断言，绿门数不等于门数。"
> "写完任何门，先在'已知坏'的状态上跑一次，看它会不会红。"
> "空门比没门更坏。"

负控（negative control）＝**故意注入一个已知的破坏，检查门/测试必须变红，然后还原**。这是唯一能证明"绿"有意义的动作。测试学上的正式名字是 mutation testing："introducing small deliberate changes (mutants) into source code and checking whether the existing test suite detects them"。

为什么非做不可——真实血泪：一次门的极性写反，五道门全绿，结果把运行时版本从 22 降回了 20.20.2，没人发现。

> 手工做这套动作容易漏，所以本仓库提供 `tools/negctl.py`：它把"命中次数、基线前置、还原哈希"变成不可跳过的前置条件。下面的"负控四式"是它的手工版说明书。

---

## 负控四式

### 式一：短路式（最快，适合校验逻辑）

把校验条件短路，看计数是否如预期变化，还原后比对哈希。

```
改动：把 if (badDate) 改成 if (false && badDate)
跑：PASS=35 FAIL=0  →  PASS=30 FAIL=5
还原：sha256 与改动前一致
```

负控红了 5 条 ⇒ 那 5 条断言是真的在干活。

### 式二：抬基线式（适合版本/阈值类门）

把门的期望值抬到不可能达到，看是否 FAIL 且 rc=1。

```
改动：基线版本 22.x → 22.99.0
跑：FAIL=2 rc=1
还原：按备份还原、哈希一致
```

### 式三：注入真值式（适合数据/合同类）

在已知好的数据里注入一个非法值，看门是否精确点名它。

```
前置：基线门必须绿（堵"门本来就红 ⇒ 负控误报合格"的假阳性通道）
注入：数据里塞一行 `2026-10-23 22:3x`（非法时刻）
跑：门必须点名这一行，且 invalidRowCount 精确 +1
还原：删掉该行
```

### 式四：变异式（适合代码分支）

删掉一个关键分支或改坏一个判断，看测试是否转红。**必须先断言"替换真的命中了"**，否则改了个不存在的字符串，负控是假的。

```js
assert.notEqual(mutated, original, '负控前提：替换必须真的命中')
// 然后跑测试，判据必须转红
```

## 三条硬规则

### 规则一：基线前置

**注入之前，门必须是绿的。** 否则你会遇到"门本来就红，注入后还是红 ⇒ 我以为负控成功了"。

```
① 跑门，确认绿（基线）
② 注入破坏
③ 跑门，确认红，且红在你注入的那个点上
④ 还原
⑤ 跑门，确认回到绿
⑥ 还原物哈希 == 原物哈希
```

### 规则二：逐发还原 + 同一次运行内核哈希

一个脚本里连做多次注入时，**不许只在最后统一还原**。第二发会继承第一发的改动，报的"咬点"其实是第一发的——读数无效。

```
注入 A → 跑 → 还原 A → 核 A 的哈希
注入 B → 跑 → 还原 B → 核 B 的哈希
```

`negctl.py` 的设计就是**一个进程只做一发**，用进程边界代替这条纪律。

### 规则三：负控样本本身也要验

拿一个"已知坏"的样本来做负控时，**先确认那个样本真的坏**。

实测：拿 `origin/main` 的 tip 当负控样本，结果 rc=0——因为那个提交本身没问题。**负控样本本身不验，就是假负控。**

## 门内自带负控（推荐写法）

把负控写进门自己，每次运行都自证一次。三种已验证的形态：

**① 四发注入全红才算 PASS**
```
负控：把门自己弄红，证明它拦得住（空门比没门更坏）
… PASS 负控 4/4
```

**② 探测器自证**
```
⑦ 负控：探测器本身能抓到"坏源码"（证明上面几条不是假绿）
```

**③ 变异测试 + 命中断言**
```js
assert.notEqual(mutated, original, '负控前提：替换必须真的命中')
// 删分支后判据必须转红
```

**④ 探针退出码三档，坏掉的探针绝不许被读成"安全"**
```
0 = 全绿
1 = 有 FAIL
2 = 探针自己坏了  ← 这一档最关键
```

`tools/check_report.py` 和 `tools/negctl.py` 都采用第四种：`2` 表示工具自己没能跑起来，与 `1`（有真问题）严格区分。

## 发布门的负控

发布前置门的负控做法：用 `git commit-tree` 造一枚**不可达提交**，`git merge-base --is-ancestor` 必须 rc=1。

反面教材也在册：新加的"未推远端不许出包"门只核**单向祖先**，一棵落后远端 10 笔的树照样绿——**门写了，但没做负控，所以没发现它拦不住真正要拦的东西。**

---

## 什么时候必须做负控

| 场景 | 要不要负控 |
|---|---|
| 新写了一道门/一个测试 | **必做**。不做你不知道它是活的 |
| 改了门的判据逻辑 | **必做**。改完的门可能比改前更松 |
| 说"我修好了" | **必做**。修好 = 注入同款破坏会红 |
| 说"0 命中 / 没发现问题" | **必做阳性对照**。先喂已知样本必须被抓，否则 0 是探针失灵 |
| 纯文案/格式改动 | 可不做 |
| 已有门覆盖且上次负控刚做过 | 可复用上次结论，但要在报告里注明"负控于 X 时做过" |

---

## 报告里怎么写

```
负控：短路式
  改动：src/xxx.ts:42 的 if (badDate) → if (false && badDate)
  命中：出现 1 次（要求 1 次），替换确实生效
  基线：PASS=35 FAIL=0（rc=0）
  注入后：PASS=30 FAIL=5（rc=1）
  还原：sha256 a1b2c3… == 改动前；复跑 rc=0
  判定：5 条断言确实在干活，非假绿
```

这个格式 `tools/check_report.py` 认得（E009 会检查四个要素：注入、基线、还原、哈希）。`negctl.py` 的成功输出可以直接贴。

**负控失败也要如实写**——写清哪一发没红、推断为什么、这条断言现在是什么状态。不许把"负控没跑成"写成"负控通过"。
